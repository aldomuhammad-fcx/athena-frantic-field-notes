What is Frantic?

Frantic is a bounty marketplace for agents. Sponsors fund specific jobs; workers claim a slot, provide the required artifacts, and can be paid USDC on Base after acceptance. That last step matters: a bounty being funded, or even marked delivered, is not proof that our agent got paid.

What we actually tried

Our agent, ATHENA / athena-fv01, runs Python workflows through Android Termux with human approval. On 6 November 2026, the Frantic MCP server initialized successfully using protocol 2025-03-26. Our first read client nevertheless reported zero readable tools. That was our bug, not evidence of a broken server: we had expected names like read_board, while the server exposed namespaced names like frantic.read_board.

We corrected the name matching, and subsequent first-party MCP reads returned the agent's standing and current bounty contracts. The account was eligible for limited paid work up to $10, with a payout rail recorded. Its own Frantic status still showed earnedUsd: 0 and paidBounties: 0.

The claim that expired

One earlier claim, bounty #142, expired before a valid delivery. That job needed a real Nitrosend campaign approval loop with an existing send receipt, a physical mailing address, Safe Mode, MAP verification, and a fresh approval receipt. We had not satisfied all those dependencies. The right lesson was not “claim faster”; it was to verify the delivery path before starting a timed claim.

We did run software, but that is not a paid delivery

For bounty #145, we verified NitroMTA v0.2.2's Linux ARM64 archive against its release SHA256 and GitHub build attestation. We installed Debian 12 inside PRoot-Distro, ran the binary without root privileges (UID 999), and discovered a missing CA trust store. After installing system CA certificates, a real NitroMTA process answered HTTP 200 at 127.0.0.1:9090/capture.

We also prepared a separate configuration targeting outbound port 2525 and generated a DKIM key. We did not send any external email or obtain a sponsor receipt. By the time we rechecked the first-party board, #145 was funded but full: 100 of 100 slots occupied. That is a useful failure to report. Technical readiness and economic eligibility are separate things.

What worked and what did not

  • Worked: the public Frantic MCP endpoint answered and exposed structured eligibility, capacity, deliverable names and review checks.
  • Worked: a short, source-verified binary could run inside an isolated ARM64 Debian userland on an Android phone.
  • Did not work: our first MCP tool-name matcher hid tools the provider actually offered.
  • Did not work: a time-limited claim was started before its external prerequisites were ready; it expired.
  • Did not work: one promising funded bounty filled before we could submit any proof.
  • Still unproven: a complete claim → original worker → delivery → accepted → paid transaction for our own agent.
“Funded” describes the job. “Ready” describes the worker. “Paid” needs a receipt belonging to the worker. They are different statements.

What we would change

We now rank opportunities by deliverability and available capacity, not advertised reward. First read the live contract, then gather any accounts, permissions and artifacts, check the remaining slots again, and only then claim. We also stopped treating local simulated PASS results as income. A useful agent should be able to say “not paid yet” without pretending its engineering progress is revenue.
